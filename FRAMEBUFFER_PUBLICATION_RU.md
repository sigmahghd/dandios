# Карантинная публикация дескрипторов framebuffer: только программный эксперимент

**Это не загрузка XNU на Redmi 9A, не работающий экран, не iOS и не прошивка.**
Новых flashable-образов этот этап не создаёт. Телефон для него не нужен.

## Что реально выполняется

В ограниченном Unicorn/Capstone-прогоне исполняется машинный код собранного XNU.
Прежний эксперимент с `arm_vm_init` сохранён отдельным сценарием: его фактический
RET, восстановленный SP и переход на сохранённый адрес вызывающего кода проверяются.
Далее `_pmap_map_bd_with_options` строит PTE для framebuffer.

Добавлен отдельный флаг `--framebuffer-publication-model`; он требует всех предыдущих
явных флагов модели. Без него прежняя остановка перед первой внешней leaf-PTE
остаётся неизменной. Модель не подменяет XNU-функцию готовым успешным возвратом.

## Результат на совпадающей паре ядро/CPU-model из CI 40306862014

- 1 210 656 instruction-hook событий ядра против 1 101 482 на прежней границе.
- 10 ранее разрешённых публикаций пустых L3-таблиц; 71 защищённая страница таблиц.
- **1150 последовательно построенных leaf-дескрипторов**, 4096 байт каждый.
- Диапазон PA: `[0x7ec50000, 0x7f0ce000)`; VA: `[0xfffffff029000000, 0xfffffff02947e000)`.
- Это **4 710 400 байт = 2944 × 1600**, один буфер по захваченному шагу строки.
  Это не вся резервация 14 131 200 байт и не доказательство текущего scanout.
- Дескриптор первого листа `0x6000007ec50607`: MAIR index1 = **0x44**, Normal
  Inner/Outer Non-cacheable, AF=1, SH=2, AP=0, PXN=UXN=1. Это **не Device memory**.
- Для каждого STR наблюдается реально пройденная пара branch / DSB ISHST;
  1150 барьеров записаны с instruction-hook номерами. Сам эффект барьера на железе
  моделью не доказан.
- Остановка **до исполнения второго `TLBI VMALLE1IS`**, в
  `_pmap_map_bd_with_options + 548`. Никакой новой генерации переводов не активируется.

Из короткого read-only дизассемблирования видно, что после этой TLBI в бинарнике
следуют DSB ISH и ISB. Эти будущие инструкции НЕ исполнялись в данном сценарии;
наличие кода не считается доказательством завершённого обслуживания TLB.

## Что разрешено и что запрещено

Перехватывается только точная форма `STR Xt, [Xn]` без смещения/writeback.
Исходная инструкция пропускается до её исполнения, после строго проверенного
host-side изменения ровно восьми байт. Страницы таблиц во всех гостевых алиасах
остаются RO. Проверяются фактические права Unicorn, исходный нулевой PTE,
хеш всей страницы, один TTBR1/L3 reference и принадлежность новой таблицы
журналу предыдущего empty-table этапа.

Допускаются только последовательные PA от начала измеренной framebuffer-резервации,
последовательные VA внутри уже карантинированных диапазонов и точные атрибуты
текущего эксперимента. CPU-контекст фиксируется; другие RAM/MMIO/валидные PTE,
другие атрибуты, повторные записи и превышение лимитов отклоняются.

**Не создаётся ни одного usable framebuffer alias и ни байта framebuffer backing.**
Прямые обращения остаются unmapped; AT в карантинный диапазон отвергается.
Нельзя исполнять через эти PTE или считать их видимыми для реального CPU/GPU.
Все конечные страницы таблиц сверяются с разрешённым состоянием.

## Проверки

- `tests/test_framebuffer_publication.py`: 46 unit-тестов, включая реальный
  Unicorn code-hook/skip, отсутствие writeback, RO fault, отсутствие backing,
  некорректные PA/атрибуты/контекст/хеши/лимиты.
- `tests/validate_framebuffer_publication.py`: независимый stdlib-only replay
  всех leaf-записей начиная с нулевых дочерних таблиц, перед/после хеши каждой
  записи, итоговые хеши, карантин, RET/SP/caller и связь каждого STR с DSB.
- `tests/test_validate_framebuffer.py`: 24 mutation-теста на настоящем отчёте,
  а не заранее сгенерированных «успешных» данных.
- Старый empty-table сценарий запускается и валидируется отдельно.

## Следующая настоящая граница

Нужна отдельная, консервативная модель повторного обслуживания TLB/публикации
leaf-переводов, затем явно обозначенный программный framebuffer backing и его
отдельные правила доступа. Только после этого можно исследовать следующий
вызов XNU. Это не заменяет проверку MMU/кешей/ATF/watchdog/дисплея на телефоне.
До полноценного устройства остаются драйверы, IRQ/таймеры, накопитель и userspace;
никакого обещания сроков или готовности iOS этот тест не даёт.
