# Dandelion: регистровая диагностика кэшей, НЕ iOS/XNU

## Зачем
Модель XNU дошла до `cpu_init`, но остановлена на неизвестном `CLIDR_EL1`. Выдавать типичные параметры Cortex-A53 за измеренные на телефоне нельзя. Этот отдельный тест читает реальные CLIDR/CTR/DCZID/CCSIDR и MMFR, а также DFR0/1, PFR0/1, ISAR0/1 и REVIDR для следующих шагов CPU-init, чтобы убрать конкретную неопределённость. Он НЕ запускает XNU, Android или iOS. Успешные host-тесты НЕ означают успешный запуск на устройстве.

В предоставленном ранее expdb-v4 обнаружен ATF watchdog-снимок x00..x29, LR, PC, SP и PSTATE на CPU0 в EL2. Это подтверждает наличие канала диагностики у прошлой Stage0, но НЕ гарантирует снимок нового теста.

## Что выполняет probe
- 4096 байт ARM64 Image, Cortex-A53 CPU0/EL2; загрузочный адрес 0x40080000.
- Проверяет EL, MIDR, MPIDR, CNTFRQ=13 MHz, SCTLR/HCR, указатель FDT.
- Не использует стек, загрузки/записи данных, framebuffer, MMIO, storage, SMC, cache maintenance. Сам загрузчик при загрузке и firmware watchdog работают отдельно.
- Маскирует исключения DAIF, устанавливает собственные EL2-векторы; временно меняет CSSELR для чтения существующих L1/L2 и восстанавливает CSSELR на успешном пути. При исключении восстановление не гарантировано; выполнение паркуется до reset.
- Сохраняет результаты в регистрах и паркуется. **Экран остаётся с логотипом Redmi; зелёных строк нет.** Ожидается firmware watchdog-reset примерно как прежде; точное время и сохранение expdb не гарантированы.
- Декодер принимает только полный CPU0-снимок с DONE-маркером, build-tag именно этого комплекта, правильным PC, EL, валидностью полей и восстановленным CSSELR. Пропуски никогда не считаются нулями.

## Прежде чем пробовать
**Это новый, не проверенный на телефоне экспериментальный Boot. Возможны зависание/бутлуп. Не для основного телефона.** Только тот же Redmi 9A dandelion с разблокированным загрузчиком и уже проверенным входом кнопками в fastboot/OrangeFox. Нужны заряженный телефон, надёжный кабель и работающий откат. Не менять recovery/LK/LK2/preloader/vbmeta/expdb/разметку, не выполнять format/erase/wipe, не блокировать загрузчик. Установленный Android заменяется только на время теста в разделе Boot; это не гарантирует сохранность данных.

Нужны исходные резервные копии именно этого телефона, 67108864 байт каждая:
- boot-current.img SHA256 `bffe6eb1d869f07a598677d92d23bf14b9b139ac04e1777ac8e1cc33b40d8362`
- recovery-current.img SHA256 `dfcbbae0ed49b6484c601cc8cc6253d27d056c61db53c8bf2f220712f13affed`

Две эти копии не являются полным бэкапом телефона. Не публиковать исходные Boot/DTB/expdb на GitHub.

## 1. Офлайн-создание на Windows
Скачать артефакт `dandelion-REGISTER-PROBE-EXPERIMENTAL-...`, полностью распаковать в новую папку. Поместить рядом с prepare_on_pc.py папку `dandelion-backup` с двумя исходными .img и manifest.json. Открыть CMD в папке комплекта (Python 3.10+ и актуальные adb/fastboot в PATH).

```bat
py prepare_on_pc.py --backup dandelion-backup --out candidate --experimental-register-probe-only
```

Скрипт не подключается к телефону, не прошивает, не меняет резервные копии. Проверяет обе SHA, извлекает точный DTB из своего Boot, проверяет SHA DTB/сырого probe/avbtool; создаёт Boot v2 с непустым техническим ramdisk и AVB hash-footer **NONE, без криптографической подписи**. Проверяет контейнер и повторно хэширует оригиналы. Только после успеха переименовывает .part в `candidate\cache-probe-boot.img`.

Если STOP/ошибка — **ничего не прошивать**, .part нельзя использовать. Нельзя брать DTB/Boot от другого аппарата или обходить проверки. `candidate-report.json` содержит SHA кандидата; она меняется между CI-запусками из-за build-tag.

## 2. Только один диагностический запуск
Если откат кнопками недоступен — остановиться. Команды выполнять по одной, проверяя результат. Если телефон сейчас в Android/OrangeFox, сначала:

```bat
adb reboot bootloader
fastboot devices
fastboot getvar product
fastboot getvar unlocked
```

Должен быть единственный нужный аппарат, `product: dandelion`, `unlocked: yes`. При отличии остановиться. Ещё до записи иметь команду восстановления и путь к исходному Boot:

```bat
fastboot flash boot "dandelion-backup\boot-current.img"
fastboot reboot
```

**Это команды отката; не запускать их вместо теста, если он ещё не записан.** Сам тест записывается отдельно:

```bat
fastboot flash boot "candidate\cache-probe-boot.img"
fastboot reboot
```

`Sending` и `Writing` должны быть OKAY. **Не использовать `fastboot boot`: на этом аппарате он ранее не выполнял предоставленный образ.**

Логотип Redmi и затем один watchdog-reset — ожидаемый сценарий, не загрузка системы. После первого reset сразу войти кнопками в fastboot и выполнить команды отката выше. Не держать телефон в повторных циклах. Если около 3 минут нет reset, принудительно войти кнопками в fastboot и откатить; отсутствие reset/дампа не доказывает ни успех, ни конкретную причину отказа. Если fastboot недоступен — использовать уже проверенный вход в OrangeFox; не экспериментировать с загрузчиком и security-разделами.

## 3. Получить только нужные данные
После отката убедиться, что Android загрузился:

```bat
adb shell getprop sys.boot_completed
adb reboot recovery
adb devices
adb shell id
adb shell getprop ro.bootmode
```

Нужны `1`, затем recovery, uid=0, bootmode=recovery. Если ADB ещё не появился, дождаться recovery; не повторять прошивку ради логов.

```bat
py read_expdb.py --out cache-expdb
py decode_cache.py --dump cache-expdb\expdb-current.bin --out cache-profile.json
```

Декодер автоматически берёт `probe-manifest.json` из этой же папки. Не смешивать комплекты разных CI-запусков. При успехе прислать **cache-profile.json** — выбранные регистры/геометрия без полного дампа. При STOP прислать точную ошибку, не прошивать заново. Сырой expdb может содержать приватную диагностику. Декодер также принимает ZIP с ровно одним expdb-current.bin, но не извлекает архив на диск.

## Проверки и ограничения
`test_probe.py` исполняет настоящий собранный машинный код в Unicorn, но системные регистры там **явно синтетические**. Проверяются отсутствие обращений к данным, разрешённые записи системных регистров, возврат CSSELR, ранние отказы, exception-vectors, строгий parser, поддельные/неполные/смешанные кадры, контейнер/AVB. Синтетические значения не выдаются за регистры телефона. Снимок пользователя не является криптографической аттестацией.

XNU пока работает только в ограниченной программной модели. Реальные MMU/cache-coherency, interrupts, timer IRQ, память LK/ATF, USB/storage/display/touch и iOS userspace этим тестом не реализуются. Новый probe — измерение, а не «готовая прошивка». Никаких обещаний полноценного iPhone на Helio G25.

## Импорт измерений в CPU-модель (на компьютере/CI, НЕ на телефоне)
В `tests/emulate_image_handoff.py` добавлен необязательный `--cache-profile cache-profile.json` вместе с `--virtual-bootstrap --kernel ...`. Семь прежних базовых сценариев выполняются без изменений, затем отдельный сценарий использует выбранные регистры и CCSIDR согласно реально выбранному CSSELR. Отсутствующий регистр/неизмеренный селектор останавливает модель, а не становится нулём. Счётчик в этом сценарии по-прежнему **синтетический**, аппаратных IRQ нет. Никакого продвижения за cache-init на реальных измерениях пока не заявляется: профиль телефона ещё не получен.

В модели также устранён опасный no-op для `DC ZVA`: это операция записи нулей в память, поэтому теперь на ней происходит явная остановка. Пропускать её как обычный cache maintenance нельзя.
